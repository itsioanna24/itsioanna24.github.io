Language Comparison

🐍 Python FastAPI + Uvicorn
  • Functional / procedural with decorator-based intent registration — concise and expressive
  • 900 lines of code — dynamic typing enables rapid development cycles
  • Response time: 0.002s — near-instantaneous startup, minimal configuration overhead
  • Async/await architecture for superior I/O-bound concurrent request handling
  • Pydantic auto-validation integrates security at the framework level
  • 6 explicit dependencies in requirements.txt — rapid environment reproduction
☕ Java Spring Boot + Maven
  • Object-oriented via Chain of Responsibility pattern — enforces explicit class hierarchy
  • 1,948 lines of code (2.16× more verbose) — static typing requires explicit declarations
  • Response time: 0.001s — 0.479s startup overhead from framework initialisation
  • Threading model with connection pooling — effective in CPU-bound scenarios
  • Spring Security, CSRF protection and role-based access for enterprise-grade security
  • Maven pom.xml with transitive dependency resolution and automated security scanning

Empirical Results

Overall Reflection

What did implementing both languages reveal?

The most surprising finding was the performance result: Java's 0.001s vs Python's 0.002s is a negligible real-world difference, yet Java is 2.16× more verbose. This challenged the assumption that compiled, statically-typed languages always win on performance. For I/O-bound chatbot applications, the framework's async architecture matters more than language-level execution speed. The practical takeaway: language choice should be driven by team expertise, security requirements, and operational context — not by performance benchmarks alone.

How did the chatbot connect Parts A and B?

Implementing an AI chatbot for Part A and then critically evaluating AI risks for Part B created an unusual and productive tension. I built the technology and immediately had to analyse its vulnerabilities. The adversarial attack and data poisoning risks discussed in the presentation are directly applicable to the chatbot's intent-matching logic — a sufficiently crafted input could potentially manipulate the regex-based Rule engine. This made the security analysis in the presentation feel earned rather than abstract.

What did the presentation format demand?

Compressing a 20-minute spoken argument into 10 slides required deciding what the slides were for — they are not the argument, they are anchors for the argument. The most challenging slide to design was the security pyramid (Slide 6): layering four threat types in ascending impact order forced a structural decision about which risk is foundational and which is most visible. Data poisoning at the base (invisible, systemic) and deepfakes at the apex (highly visible, public-facing) was a deliberate choice that the transcript then had to justify.

What would I extend if given more time?

For Part A, I would add load testing results at higher concurrency (100+ simultaneous users) where the async/threading difference between FastAPI and Spring Boot becomes meaningful, and where Python's GIL becomes a genuine constraint. For Part B, I would extend the case study analysis to include the EU AI Act's first enforcement actions — the regulation came into force in 2024, and its practical impact on enterprise AI governance is now observable, not speculative.
