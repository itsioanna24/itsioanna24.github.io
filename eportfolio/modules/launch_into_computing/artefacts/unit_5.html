Overview

This assignment uses the publicly available Airbnb European City Dataset, which covers listings across ten major cities — Amsterdam, Athens, Barcelona, Berlin, Budapest, Lisbon, London, Paris, Rome, and Vienna. Using Python with Pandas, Seaborn, and Matplotlib, the dataset was loaded, cleaned, and analysed to surface pricing patterns across cities and day types. A 200-word reflection then compares SQL and NoSQL storage models in the context of this dataset's structure and use case.

Part 1 — Python Analysis

The analysis followed a three-stage pipeline: loading and merging per-city CSV files, cleaning the unified dataframe, and computing descriptive statistics before producing visualisations.

01 — Load

Import & Merge

All city CSV files from the data/ folder were looped over, tagged with a city column, and concatenated into a single dataframe using pd.concat().

02 — Clean

Standardise & Filter

Duplicates removed, realSum renamed to price, rows with missing prices dropped, and outliers outside €10–€1,000 filtered out.

03 — Analyse

Describe & Correlate

City and day-type columns extracted via regex. Mean, median, group averages, and numeric correlations computed with Pandas aggregations.

Part 2 — Storage Model Reflection

The reflection below (≈200 words) compares SQL and NoSQL database models in the context of this dataset's structure and analytical requirements.

Reflection Report: SQL vs. NoSQL for the Airbnb Dataset

For the analysis of Airbnb listings across major European cities, the dataset was highly structured, tabular, and contained consistent fields such as price, room_type, city, person_capacity and various numerical indicators like cleanliness_rating and metro_dist. This structured format makes a relational database (SQL) the most appropriate choice for storing and analysing this data.

Using SQL databases such as PostgreSQL or MySQL would allow for efficient querying, filtering, grouping and joining operations (Alkin Tezuysal and Ahmed, 2024). For example, calculating the average price by city or correlating room capacity with price using SQL operations such as GROUP BY and JOIN. SQL's schema enforcement also ensures data consistency and integrity, which is crucial when working with standardised fields like booleans and floats (Alkin Tezuysal and Ahmed, 2024).

Alternatively, NoSQL databases such as MongoDB are better suited to semi-structured or evolving data formats (Taipalus, 2024) — for instance, user reviews or nested booking metadata — fields not present in this dataset. While NoSQL offers flexibility, it does not provide the same level of built-in support for complex analytical queries as SQL, making it less suitable for this use case.

In conclusion, given the dataset's clean structure and analytical focus, a relational SQL database would be ideal for both storage and querying in this project.

Storage Model Comparison

Criterion SQL (PostgreSQL / MySQL) NoSQL (MongoDB)
Data structure Fixed schema — ideal for this tabular dataset Flexible schema — suited to nested / evolving data
Analytical queries ✓ Strong — GROUP BY, AVG, JOIN ✗ Limited — aggregation pipelines less expressive
Data integrity ✓ Enforced — types, constraints, ACID Relaxed — schema-on-read, no type enforcement
Scalability Vertical — complex sharding for horizontal scale ✓ Horizontal — built for distributed workloads
Best for this dataset? ✓ Yes — clean, typed, analytical ✗ No — would suit review / metadata extensions
Verdict SQL is the recommended storage model for this structured, query-heavy Airbnb dataset.

Overall Reflection

What did I learn from the data cleaning process?

Cleaning the dataset was more demanding than expected. Handling the city column — which encoded both city name and day type in a single string — required regex extraction, an approach I had not previously used in a data pipeline. This reinforced that real-world datasets require creative parsing, not just null removal.

What did the visualisations reveal?

The city-level bar chart made Amsterdam's premium immediately legible in a way that descriptive statistics alone could not. The weekday/weekend comparison showed that pricing strategy varies significantly by city — a pattern invisible in a single average. Choosing the right chart type was itself an analytical decision, not just a presentational one.

What did the storage reflection add?

Thinking about database storage forced me to articulate why the dataset's structure matters beyond the analysis itself. The insight that the same data could justify different storage choices depending on whether future extensions include unstructured content (reviews, photos) was new and practically valuable.

What would I improve in future work?

I would extend the correlation analysis to include additional features — superhost status, distance to city centre, cleanliness rating — to build a richer understanding of what drives price. I would also explore cloud-native storage options such as Google BigQuery, which combines SQL querying with horizontal scalability, as a more production-ready alternative to local PostgreSQL.
